# 얇은 전체 흐름 먼저 (Thin slice first) — 진행 방식 설계

| 항목 | 내용 |
|---|---|
| 상태 | 승인 대기 |
| 작성일 | 2026-11-18 |
| 관련 문서 | `SPEC.md` v1.2, `PRD.md` v1.1, `AGENTS.md`, `docs/tasks/BOARD.md` |

## 1. 목적과 이유

- 프로젝트 목적은 **학습**이다. agentic 병렬 개발, 데이터 수집 파이프라인, 시계열 예측을 직접 경험하는 것이 목표다.
- 가장 오래 걸리는 것은 데이터 축적(8주 이상)이다. 그래서 수집을 최대한 빨리 시작하고, 기다리는 동안 나머지를 깊게 만든다.
- 첫 1~2주 안에 "실제 창원대로 속도가 DB에 쌓이고 화면에 뜨는" 상태를 만든다.

## 2. 목표 / 비목표 / 실패 기준

- **목표**: 1~2주 안에 수집 → DB → 5분 집계 → 기준 예측 → 대시보드가 실제 데이터로 한 번 연결된다. 이후 8주 동안 SPEC 수준으로 깊어진다.
- **비목표**: 첫 단계에서 SPEC의 모든 규칙(이상치 세부 기준, XGBoost, walk-forward, 달력 특성)을 구현하지 않는다. 시민 공개(Phase 2)는 "여유 있으면" 단계로 미룬다.
- **실패 기준**: 빨리 만들려다 핵심 불변식을 깨는 것. 결측을 0으로 바꾸기, 미래 정보 사용, 가짜 데이터를 실제처럼 표시하기, 비밀정보 노출은 v0에서도 허용하지 않는다.

## 3. 검토한 방식

| 방식 | 내용 | 장단점 |
|---|---|---|
| **A. 얇게 끝까지 먼저 (채택)** | 모든 모듈의 최소 기능으로 전체 흐름을 먼저 잇고 반복해서 깊게 만든다 | 흐름이 빨리 보이고 배울 거리가 계속 생긴다. 초기 코드는 나중에 고쳐야 한다 |
| B. BOARD 순서대로 | 계약을 모두 확정한 뒤 모듈을 완성도 있게 개발한다 | 깔끔하지만 3~4주 동안 눈에 보이는 결과가 없다 |
| C. 사용자가 직접 코딩 | 에이전트는 리서치와 리뷰만 한다 | 코드를 가장 많이 배우지만 agentic 경험 목적에서 멀어진다 |

사용자가 A를 선택했다.

## 4. Slice 0 (첫 1~2주) 범위

| 모듈 | v0에서 하는 것 | 나중으로 미루는 것 |
|---|---|---|
| 공용 (orchestrator) | git 초기화, 폴더 골격, `common/timeutil.py`(KST, 5분 내림), 로깅, 설정 | - |
| database (dev-data) | SPEC 5장 DDL 전체(작성 비용이 낮음), `db.connect`(WAL/FK), 구간·링크 시드 적재 | `calendar_info` 데이터 적재 |
| collector (dev-collector) | 경찰청 API 1회 호출 → 원본 파일 저장 → `traffic_observation` 저장, `collection_log`, 타임아웃·재시도 | ITS 보조 수집, 기상 |
| scheduler (dev-collector) | 5분마다 수집 → 집계 → 예측을 C-06 진입점으로 호출하는 단순 상주 루프 | 정교한 장애 복구 |
| preprocessing (dev-data) | 5분 bin, 구간 속도(링크 길이가 있으면 거리 가중 조화평균, 없으면 단순 평균 + 플래그), 범위 이탈 제외, 결측은 NULL 유지 | 갱신 정지(frozen) 판정, 70% 부분 관측, forward fill, as-of 특성 |
| prediction (dev-ml) | 기준 모델 1종(현재 속도 유지)으로 5·10·15·30분 예측 저장, 실제값 사후 갱신 | 나머지 기준 모델, XGBoost, 평가 테이블 |
| dashboard (dev-dashboard) | 구간별 현재 속도·예측 표, 데이터 지연 경고, 데이터가 없으면 '-' 표시 | 시계열 그래프, 히트맵, 성능 화면 |

v0에서도 지키는 것: AGENTS.md 6장 불변식 전부, 경로 소유권, 테이블 쓰기 소유권.

## 5. 계약 처리

- 계약은 Slice 0에 필요한 범위만 v1로 확정(frozen)한다. 대상은 C-01(DDL 전체), C-02(R-01 결과 반영), C-06(진입점 시그니처)이다.
- C-03(특성)과 C-04(모델 등록·평가)는 Slice 1 이후에 확정한다. v0 prediction은 C-01의 `traffic_prediction` 테이블만 사용한다.
- 이후 슬라이스에서 계약을 넓힐 때는 AGENTS.md 4.3 절차대로 버전을 올린다.

## 6. 진행 순서

```
지금      R-01~R-05 리서치 (진행 중)  ∥  T-00 저장소 초기화, T-01 공용 코드   ∥  [사람] API 신청
리서치 후  C-01, C-02, C-06 v1 확정, 공용 픽스처 생성
병렬      D-DAT-01(DB) ∥ D-COL-01(수집기) ∥ D-ML-00(기준 예측) ∥ D-DSH-00(대시보드)   ← 픽스처 기준
순차      D-DAT-02a(5분 집계 v0), D-COL-02(스케줄러)
통합      [사람] .env에 키 입력 → 실제 호출 1회 → 전체 흐름 확인 → 상시 수집 시작  = Slice 0 완료
```

## 7. 이후 슬라이스 (데이터 축적 8주 동안)

| 슬라이스 | 내용 | 시작 조건 |
|---|---|---|
| Slice 1 | 전처리 규칙 완성(frozen, 70%, forward fill), 기준 모델 3종, 평가 지표, 시계열 그래프 | 수집 1주 |
| Slice 2 | as-of 특성(C-03), XGBoost 학습·등록(C-04), 성능 화면 | 수집 2주 (파이프라인 시험) |
| Slice 3 | walk-forward 정식 평가, 달력·방학 특성, 구간별 모델 비교 | 수집 8주 |
| Slice 4 (선택) | 시민 공개(Phase 2) | 여유가 있고 공개 조건을 충족할 때 |
