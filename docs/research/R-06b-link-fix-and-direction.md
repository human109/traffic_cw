## 요약
- **ITS는 이 구간을 2026 개정 이전의 링크 ID·분할점으로 준다.** S3 꼬리에서 ITS는 `4140068800`(삼동동산7-2→삼동지하차도(서측), 역산 길이 174.6m) 한 개를 매 회차 주고, `4140068801`은 70개 원본 파일 어디에도(roadName 무관 포함) 없다. 2026 배포본에도 `4140068800`은 없고, 같은 길을 `4140071400`(362.8m)의 하류와 `4140068801`(111.7m)로 나눠 둔다. → **수정안: S3,7 행의 link_id를 `4140068801`→`4140068800`으로 교체(길이 111.7 유지).**
- 좌표로 확인하면 `4140207700`(삼동동 산7-2)은 삼동동산7-2(4140057401, ITS 노드 4140057400에 대응)에서 하류 58.9m 떨어진 별개 지점이다. `4140071400` 행은 링크 ID가 같아 관측이 계속 들어오므로 **변경 없음**이다(ITS 관측 범위 307.0m vs 가중치 362.8m의 차이는 아래에 근거와 함께 기록).
- S6 측도 `4150149001`(성주지하차도→성주광장, 190.5m)은 ITS가 어떤 ID로도 주지 않는다(같은 ITS 노드쌍에는 본선만 1개, 측도는 반대 방향 `4150149101`만 있음). → **행 유지(변경 없음)**. 현재 본선만 집계하는 v0에는 영향이 없고, Slice 1 `speed_side`에서 S6만 상시 결측(NULL)이 된다.

CSV에는 `valid_to` 열이 없어 로더만으로는 안 되며, DB 수정 절차는 오케스트레이터가(dev-data 소유 경로) 결정한다. 과거 bin의 속도값은 `4140068801`이 관측된 적이 없어 어느 방식으로 반영해도 같고, 기대 링크 수·플래그만 절차에 따라 달라질 수 있다.

## 방향 속도 비교 절차(쿼리 — 2부에서 실행한 것)

**데이터와 시간 창**: 운영 DB `data/traffic.db`를 읽기 전용으로 연다. 파이썬 `sqlite3.connect("file:data/traffic.db?mode=ro", uri=True)` 또는 CLI `sqlite3 -readonly data/traffic.db`. 대상 관측은 `source='its'`, `quality_flag='ok'`, `speed>0`이고 `source_timestamp`가 `2026-11-20T07:00:00+09:00` 이상 `09:00:00` 미만이다(SPEC 8장 평가 창 07:00~09:00; `source_timestamp`는 `to_iso` 고정 형식이라 문자열 비교가 안전하다). 2026-11-20은 금요일이고 공휴일 여부는 운영 DB `calendar_info`로 확인한다(R-05 파이프라인이 채운다). 반대 방향 관측은 C-02 v2의 저장 범위(창원대로 양방향) 덕분에 이미 DB에 쌓인다(발견 #11) — 별도 수집이 필요 없다.

**방향 매핑**: 우리 방향 = `segment_link`(`is_mainline=1`) 33행(S0 3 + S1 5 + S2 6 + S3 5 + S4 3 + S5 8 + S6 3). 반대 방향 = 링크 ID−100(`printf('%010d', CAST(link_id AS INTEGER)-100)`). 근거는 발견 #10(37쌍 전부 −100). 측도(`4150149001`)는 −100 규칙이 어긋나므로 본선만 비교한다. 쿼리 1~3은 2026-11-19 10:00~12:00 창으로 운영 DB(읽기 전용)에서 실행해 문법과 −100 매핑을 검증했다. 그 창에서 구간별 ours/opp가 이미 크게 갈렸다(예: S0 ours 23.7 vs opp 14.1, S6 ours 41.2 vs opp 21.0 km/h) — 방향 비교 방법이 실제로 차이를 잡아낸다는 뜻이다. 같은 실행에서 q3는 예상대로 `4140068801`·`4150149001`만 가렸다.

**쿼리 1 — 구간 × 방향 요약**(길이 가중 조화평균은 preprocessing과 같은 식이지만 링크별 bin 대표값 선별은 생략한 방향 비교용 단순 집계다. preprocessing 기준이 필요하면 우리 방향은 `segment_traffic_5min.speed`를 쓰고 반대 방향만 이 쿼리로 계산해 나란히 놓는다):

```sql
WITH seg AS (
    SELECT segment_id, link_id AS obs_link, link_length_m AS w, 'ours' AS dir
    FROM segment_link WHERE is_mainline = 1
    UNION ALL
    SELECT segment_id, printf('%010d', CAST(link_id AS INTEGER) - 100),
           link_length_m, 'opp'
    FROM segment_link WHERE is_mainline = 1
)
SELECT dir, segment_id,
       ROUND(SUM(w) / SUM(w / o.speed), 1) AS kmh_weighted,
       ROUND(AVG(o.speed), 1)              AS kmh_simple,
       COUNT(DISTINCT o.link_id)           AS n_links_observed,
       COUNT(*)                            AS n_obs
FROM seg s
JOIN traffic_observation o
  ON o.link_id = s.obs_link
 AND o.source = 'its' AND o.quality_flag = 'ok' AND o.speed > 0
 AND o.source_timestamp >= '2026-11-20T07:00:00+09:00'
 AND o.source_timestamp <  '2026-11-20T09:00:00+09:00'
GROUP BY dir, segment_id
ORDER BY segment_id, dir;
```

**쿼리 2 — 15분 버킷 프로파일**(정체 시작·종료 시각 확인. `bucket_15min`은 0=00:00 기준 15분 단위, 28=07:00, 35=08:45. 위 `seg` CTE를 같이 쓴다):

```sql
SELECT s.segment_id, s.dir,
       (CAST(substr(o.source_timestamp, 12, 2) AS INTEGER) * 60
        + CAST(substr(o.source_timestamp, 15, 2) AS INTEGER)) / 15 AS bucket_15min,
       ROUND(AVG(o.speed), 1) AS kmh,
       COUNT(*) AS n_obs
FROM seg s
JOIN traffic_observation o
  ON o.link_id = s.obs_link
 AND o.source = 'its' AND o.quality_flag = 'ok' AND o.speed > 0
 AND o.source_timestamp >= '2026-11-20T07:00:00+09:00'
 AND o.source_timestamp <  '2026-11-20T09:00:00+09:00'
GROUP BY s.segment_id, s.dir, bucket_15min
ORDER BY s.segment_id, s.dir, bucket_15min;
```

**쿼리 3 — 창에서 빠진 링크 확인**(관측 0건 링크 목록. 제안 1 반영 전에는 `4140068801`, `4150149001`이 여기 나온다):

```sql
SELECT sl.segment_id, sl.link_id, sl.is_mainline, COUNT(o.id) AS n_obs
FROM segment_link sl
LEFT JOIN traffic_observation o
  ON o.link_id = sl.link_id AND o.source = 'its' AND o.quality_flag = 'ok'
 AND o.source_timestamp >= '2026-11-20T07:00:00+09:00'
 AND o.source_timestamp <  '2026-11-20T09:00:00+09:00'
GROUP BY sl.segment_id, sl.link_id, sl.is_mainline
HAVING n_obs = 0;
```

**판정 기준(제안 — 판단이므로 오케스트레이터가 확정)**: 출근 방향은 소계광장→성주광장(남동쪽, 방위각 약 124°, R-03b #10)이므로 아침에 우리 방향이 맞다면 `ours`가 `opp`보다 낮아야 한다. 모든(또는 대부분의) 구간에서 07:00~09:00 가중 평균이 `ours < opp`이고 07:30~08:30 버킷에서 `ours`가 `opp`보다 20% 이상 낮으면 방향 설정 적중으로 본다. 반대로 `ours ≥ opp`가 다수 구간에서 나오면 SPEC 3.3의 방향 설정이 틀렸을 가능성이 있으므로 재검토 CR을 낸다.
